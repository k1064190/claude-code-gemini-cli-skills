3단계

격리된 콜드 인스턴스로 실행되는 claude -p 서브에이전트 스킬을 추가하고, 공식 문서가 잘못 설명하고 있던 세 가지 사실을 바로잡습니다.

Claude Subagent Skill

왜

이 저장소는 세 개의 외부 CLI(codex, gemini, agy)에는 위임하고 있었지만 Claude Code 자체에는 위임하고 있지 않았습니다. claude -p 서브에이전트는 "다른 관점의 의견"을 얻기 위해서가 아니라 격리(isolation)를 위해 둘 가치가 있습니다. 대화 기록이 없는 콜드 인스턴스, 범위가 제한된 --allowedTools, 독립된 프로세스라는 특성은 병렬 서브태스크, 권한이 제한된 편집, Codex/Antigravity로부터의 오케스트레이션에 유용합니다.

~/.claude/skills/claude-subagent에 예전에 작성된 개인용 사본이 있었습니다(2026-05-03 작성, 이 저장소에는 반영된 적 없음). 이를 실제 CLI로 검증한 결과 세 가지 핵심적인 부분이 잘못되어 있음을 발견했고, 그래서 최신 문서와 실측을 바탕으로 다시 작성했으며 기존 사본은 삭제했습니다.

무엇을

  • claude-subagent/SKILL.md — 새 스킬. 기본값: --model opus, --bare 사용 안 함, --output-format json, 읽기 전용 --allowedTools "Read,Glob,Grep".
  • README.md — Skills / Defaults / Requirements / Installation / Quick start / Models / Tested on 항목이 이제 Claude를 다룹니다.
  • 기존 스킬과 공식 문서 둘 다와 모순되는 세 가지 발견 사항이며, 각각 기록하기 전에 재현하여 확인했습니다.
    발견 사항 근거
    --bare는 구독(subscription) 인증에서 사용할 수 없습니다. bare 모드는 OAuth와 키체인 읽기를 완전히 건너뛰는데, 문서는 스크립트용으로 권장하면서도 이는 API 키 인증을 전제로 합니다. claude --bare -p … → 종료 코드 1, apiKeySource: "none", .result = "Not logged in · Please run /login".
    --output-format json은 2.1.209 기준으로 문서가 설명하는 단일 객체가 아니라 이벤트의 JSON 배열을 출력합니다. 공식 문서와 기존 스킬이 사용하던 jq -r '.result'는 Cannot index array with string "result" 오류로 실패합니다. 깨끗한 환경(env -i)에서도 재현되어, Claude Code 내부에 중첩되어 실행되기 때문에 발생하는 현상이 아님을 확인했습니다. 해결책: jq -r 'if type=="array" then last else . end | .result'.
    실행이 종료 코드 0을 반환하면서도 실패할 수 있습니다. .is_error가 subtype: "success"이면서도 true일 수 있고, --allowedTools에 없는 도구는 조용히 거부됩니다. 인증 실패 시 오류 설명이 .result에 담깁니다. 거부된 편집 요청은 파일이 그대로인 채로 "DONE"이라고 답했습니다 — .permission_denials만이 유일하게 정직한 신호였습니다.
    --allowedTools는 샌드박스가 아닙니다. 이는 프롬프트를 억제할 뿐 도구 자체를 제거하지 않습니다. 목록에 없는 도구는 주변(ambient) 권한 모드로 그대로 전달되며, 프로젝트 자체의 settings/hooks는 도구 경계 밖에서 완전히 실행됩니다. .claude/settings.json에서 defaultMode: bypassPermissions로 설정된 저장소를 대상으로, --allowedTools "Read,Glob,Grep"를 지정한 "읽기 전용" 호출이 32개의 도구를 제공받았고, 파일을 편집했으며, permission_denials: 0으로 보고했습니다. 해당 저장소의 PreToolUse 훅은 실행 중 셸 명령을 실행했습니다. 이 경계를 보장하려면 --tools, --permission-mode dontAsk, --setting-sources user, --strict-mcp-config 네 가지 플래그가 모두 필요합니다.

어떻게

근거가 먼저, 서술은 그다음: 스킬에 적힌 모든 주장은 문서화되기 전에 먼저 실행해 확인했습니다. Doctor Cho가 범위를 정한 핵심 테스트 다섯 가지와, 도그푸딩(dogfood) 검증 한 차례를 진행했습니다.

  1. T1 표준 호출 (--model opus) → 종료 코드 0, is_error=false, 사소한 프롬프트에 $0.41(비-bare 실행은 CLAUDE.md, 플러그인, 스킬을 로드하기 때문 — 그래서 haiku/sonnet 관련 가이드가 존재).
  2. T2 --bare → 위에서 언급한 인증 실패.
  3. T3 stdin. 첫 설계는 잘못되었습니다: sleep 300 | claude …는 타임아웃되었지만, timeout이 파이프라인 전체를 감싸고 있어서 실제 124는 Claude가 아니라 sleep에서 나온 것이었습니다. 백그라운드 writer가 열어 둔 FIFO를 사용해 timeout이 Claude만 감싸도록 다시 테스트했습니다. stdin이 열려 있지만 비어 있는 경우는 정상적으로 종료됩니다(10초. codex는 이 경우 멈춘다는 점과 다름). stdin에 데이터가 들어오지만 EOF가 없는 경우 아무 작업도 시작하기 전에 영원히 블로킹됩니다(0바이트 출력, 60초 뒤 강제 종료). 정상적인 파이프(EOF 있음)는 정상 동작하며 파이프된 텍스트가 모델에 전달됩니다. 따라서 의도적인 파이프를 사용하는 경우를 제외한 모든 호출에는 < /dev/null을 붙여야 한다는 규칙은 stage-1과 결론은 같지만 더 좁은 이유에서 나온 것입니다.
  4. T4 --allowedTools → 거부된 편집은 파일을 그대로 두고 permission_denials: 1을 남기며, 허용된 편집은 파일을 실제로 변경합니다. 자식 세션은 permissionMode: default로 실행되며 부모의 auto 설정을 물려받지 않습니다.
  5. T5 --resume → 결과 이벤트에서 session_id를 캡처했고, 후속 호출은 첫 호출에서 사용한 암호(codeword)를 정확히 기억해내며 같은 id를 재사용했습니다.

도그푸딩. 스킬 자체의 표준 호출 방식을 사용해 새 claude -p 인스턴스가 SKILL.md 자체를 감사(audit)하도록 했습니다. 그 결과 실제 결함 다섯 개를 찾아냈습니다 — 복사해서 바로 쓸 수 있어야 할 스니펫에 정의되지 않은 $ERRLOG, 표준 스니펫이 이미 rm으로 지운 파일을 읽으려는 resume 예제, 문서가 읽으라고 안내하는 오류 로그를 정리 단계가 지워버리는 문제, 그리고 가장 심각하게는 표준 블록 자체가 문서가 요구하는 세 가지 검사 중 아무것도 수행하지 않고 있던 문제입니다. 또한 호출을 | jq로 끝내면 Claude의 종료 코드가 jq의 종료 코드로 덮어써져서, timeout에 의한 강제 종료가 아무것도 출력하지 않고 종료 코드 0을 반환한다는 것도 포착했습니다 — 조용한 성공과 구분되지 않는 멈춤입니다.

테스트로 잡아낸 자체 버그. 새로 작성한 블록은 fail-closed 기본값으로 .is_error // true를 사용했습니다. jq의 //는 null뿐 아니라 false도 대체해버리기 때문에, 정상적으로 성공한 실행조차 is_error=true로 보고되었습니다. SKILL.md에서 블록을 그대로 추출해 성공 / 인증 실패 / 거부 / 타임아웃 네 가지 경로에서 실행해보니 즉시 드러났고, 수정은 명시적인 if .is_error == false로 처리하는 것이었습니다.

회고

핵심 발견 사항 대부분은 공식 문서와 모순되며, 그중 어느 것도 문서를 읽는 것만으로는 발견할 수 없었습니다 — JSON 배열 형태, 종료 코드 0인 실패, 그리고 권한 모델 문제는 모두 실제로 명령을 실행해 결과를 확인해야만 드러났습니다. 각 리뷰 레이어는 서로 다른 종류의 문제를 잡아냈고, 매번 다른 레이어가 놓친 것을 잡아냈습니다: 도그푸딩 검증은 "세 가지 신호를 모두 확인하라"고 설파하는 스킬이 정작 아무것도 확인하지 않는 표준 스니펫을 배포하고 있음을 발견했고, Codex 봇은 읽기 전용 기본값이 실제로는 읽기 전용이 아님을 발견했으며, agy는 강화된 버전조차 저장소 자체의 훅이 셸 명령을 실행하도록 허용하고 있음을 발견했습니다.

관통하는 흐름은, 여기서 고친 모든 것이 ‘사실인 것처럼 진술된 가정’에서 시작되었다는 점입니다. --allowedTools는 샌드박스처럼 들렸기 때문에 그렇게 문서화되었습니다. 리뷰어의 주장을 받아들이거나 기각하는 대신 직접 재현해본 것이 그것을 명확한 경계로 바꾸어 놓았습니다. 앞으로 이어갈 점: 문서에서 스니펫을 그대로 추출해 실행할 것(다시 타이핑한 사본은 문서의 결함을 조용히 고쳐버립니다), 그리고 ‘거부됨’과 ‘제공되지 않음’을 서로 다른 상태로 취급할 것 — .permission_denials는 거부만 기록하므로, 서브에이전트가 과도한 권한을 가졌는지는 결코 알려주지 않습니다.
