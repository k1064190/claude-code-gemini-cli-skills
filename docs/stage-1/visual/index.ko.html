Subagent Stdin Hang Fix

왜

Doctor Cho는 codex-subagent와 antigravity-subagent (agy) 스킬이 "요청이 제대로 전달되지 않고 자주 멈추는 것 같다"고 보고했습니다. gemini가 지원 중단(deprecated)된 상태라 이 두 스킬이 사실상 유일하게 지원되는 서브에이전트였기 때문에, 이 멈춤 현상은 실제 작업을 가로막고 있었습니다.

무엇을

  1. stdin 블로킹(주요 원인). codex exec "prompt"와 agy -p "prompt"는 stdin이 비TTY(non-TTY)일 때 항상 stdin을 읽습니다. EOF 없는 열린 파이프는 영원히 블로킹되며, 2>/dev/null이 그 알림 메시지를 가려 조용한 멈춤처럼 보였습니다. OpenAI codex issue #20919로 확인되었으며, 공식 우회 방법인 < /dev/null을 resume이 아닌 모든 호출에 추가했습니다.
  2. 2>/dev/null이 오류를 삼켜버렸습니다. 인증, 레이트리밋, 플래그 오류에도 stdout이 비어 있고 진단 정보가 없었습니다. 이제 stderr를 ERRLOG=$(mktemp)에 캡처하여 종료 코드가 0이 아니거나 stdout이 비어 있을 때 노출합니다.
  3. 하드 타임아웃이 없었습니다. timeout -k 10 <N>을 추가했습니다. 제한 시간에 SIGTERM을, 10초 뒤 SIGKILL을 보냅니다. 종료 코드 124 = 타임아웃, 137 = 강제 종료입니다.
  4. codex의 --full-auto는 지원 중단되어 --sandbox workspace-write로 대체되었습니다.
  5. --dangerously-skip-permissions 없이 agy의 -p를 사용하면 편집 내용이 프로젝트가 아닌 스크래치 샌드박스 (~/.gemini/antigravity-cli/scratch/)에 기록됩니다 — 이제 문서화되었습니다.
  6. codex exec resume에는 플래그를 쓸 수 없다는 기존 주장은 resume --help 기준으로 잘못된 것이었으며, 이를 수정했습니다.

어떻게

systematic-debugging 스킬을 이용해 근본 원인을 먼저 파악한 뒤 수정하는 방식으로 조사했습니다. 모든 주장은 결정론적으로 재현되었습니다(열린 파이프 상태의 stdin → 종료 코드 124; < /dev/null → 종료 코드 0; 잘못된 플래그 → stderr에 캡처됨; timeout -k는 SIGTERM을 무시하는 자식 프로세스를 종료 코드 137로 강제 종료). agy에서 발생한 40분짜리 멈춤 현상은 /proc/<pid>/fd의 파이프 아이노드(pipe-inode) 소유권을 추적하여, 에이전틱(agentic) find 손자 프로세스가 RESULT=$(…) 파이프를 열어둔 채 붙잡고 있었음을 확인했습니다. agy stdout을 파일로 캡처하고 절대 $(agy …)로 감싸지 않으며, agy가 파일을 찾아 헤매게 하지 않는 방식으로 해결했습니다. 이 결과들은 공식 codex 문서와 각 CLI 자체의 --help 출력과 교차 검증했습니다.

리뷰 루프

CLAUDE.md 규정에 따라 세 명의 리뷰어가 참여했습니다: code-reviewer-pro 서브에이전트, codex (PR #3의 GitHub 봇), antigravity-subagent(agy).

  • 1차(code-reviewer-pro + codex): 두 리뷰어가 공통으로 지적한 사항을 수정했습니다 — 인라인 스니펫의 정의되지 않은 $ERRLOG(하드 bash 오류로 검증됨), 병렬 실행 블록의 일관되지 않은 stderr 처리, fish/zsh의 읽기 전용 $status와 충돌하는 status 변수(rc로 이름 변경), "resume에는 플래그를 쓸 수 없다"는 잘못된 주장 (resume --help로 정정). codex 봇이 지적한 병렬 $ERRLOG 관련 P2는 각 병렬 호출을 독립적으로 만들어 해결했습니다. 근거를 들어 기각한 사항: codex의 --add-dir 관련 P2와 resume의 stdin - 처리에 관한 주장은 모두 표적 테스트로 반증되었습니다.
  • 2차(agy 리뷰): agy로 diff를 리뷰한 결과 실제 결함 두 가지가 드러났습니다 — 위치 인자 형태의 resume --last에 < /dev/null이 빠져 있었고, resume 예제들이 새로 도입한 stderr 캡처 규칙과 어긋나게 여전히 2>/dev/null을 사용하고 있었습니다. 둘 다 수정했습니다.
  • 가장 큰 사건 — agy의 "리뷰가 40분 걸린다" 멈춤: 스크래치 디렉터리에서 agy에게 @final.diff를 넘기자 agy의 에이전트가 파일을 찾기 위해 $HOME 전체를 훑는 find를 실행했습니다. timeout -k는 agy를 종료시켰지만 그 손자 프로세스는 종료시키지 못했고, 이 프로세스가 RESULT=$(…) 파이프를 약 40분간 열어둔 채 붙잡고 있었습니다(/proc/<pid>/fd의 파이프 아이노드 소유권으로 확인). agy의 stdout을 커맨드 치환 대신 파일로 캡처하고, agy가 파일을 찾아 헤매게 하지 않는 방식으로 해결했습니다.

회고

Doctor Cho의 두 차례 피드백이 핵심 수정을 이끌었습니다. "아무리 긴 추론이라도 5시간이 걸릴 수는 없다"는 지적은 timeout -k를 이용한 하드 타임아웃 도입으로 이어졌고, "agy가 $HOME 전체를 탐색하는 것은 말이 안 된다"는 지적은 실제 40분 멈춤 메커니즘(에이전틱 find 손자 프로세스가 커맨드 치환 파이프를 붙잡고 있던 것)을 찾아내는 계기가 되었습니다. 앞으로도 서브에이전트가 "멈췄다"는 보고를 받으면 stdin 블로킹, stderr 폐기, 그리고 타임아웃 이후에도 $(…) 파이프를 붙잡고 있는 잔존 손자 프로세스를 확인해야 합니다. 그리고 긴 에이전틱 CLI 출력은 커맨드 치환이 아니라 파일로 캡처해야 합니다.
